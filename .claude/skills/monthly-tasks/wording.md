# Правила: заголовок в трекере → название для акта клиенту

Главная задача навыка: по названию задачи в трекере сгенерировать формулировку для
официального документа. Правила выведены из практики — из пар «заголовок тикета → строка
акта» за годы работы; готовые примеры на всех языках акта лежат в `months/ГГГГ_ММ/tasks.md`
каждого месяца, и при сомнениях надёжнее посмотреть, как похожая работа формулировалась
раньше, чем изобретать заново.

Примеры ниже синтетические: ключи задач, хосты и домены выдуманы. Форма важнее содержания —
подставляй свои.

1. **Название описывает фактически сделанную работу, а не исходный заголовок тикета.**
   Заголовок в трекере часто симптом, просьба или огрызок — если по нему непонятно, что делалось,
   открой задачу (описание, комментарии) и сформулируй по сути работы:
   - `OPS-1042 «Разобраться с портами в iptables»` → «Ограничить SSH подключения между дата-центрами»
   - `SUP-2381 «проблемы с AWS Global Accelerator»` → «Отбить DDOS на сервис DNS»
   - `OPS-1187 «Разобрать показ рекламы в старом ДЦ»` → «Зачистить освободившиеся сервера и отказаться от них»
   - `SUP-2404 «DbDumpsTooOld»` → «Починить инструмент для проверки бэкапов баз PostgreSQL»

2. **Симптом → действие.** Багрепорты переформулируются как «Исправление/Восстановление/Починка …»:
   - «Нет доступа в Jenkins» → «Восстановление доступа в Jenkins»
   - «Не зайти в artifactory по LDAP» → «Восстановление доступа в Artifactory»
   - «Падает джоба mr:env-app:start» → «Исправление падения тестов из-за проблем с базой»

3. **«Ресёрч / Консультация / Просьба помочь» → конкретное действие или результат:**
   - «Ресёч alb часть 2» → «Настройка нового AWS Application Load Balancer в кластере тестовых окружений»
   - «Консультация по пробросу переменных в триггер джобах» → «Проброс переменных между пайплайнами через триггер»
   - Если работа реально исследовательская — «Подготовка …», «Сбор и анализ …», «Настройка и тестирование …».

4. **Стиль: нейтральный деловой русский, без сленга и внутренних словечек.**
   - «девчики» → «девелоперские окружения», «чекалка» → «инструмент мониторинга»,
     «жрёт трафф на внешке» → «потребление трафика на серверах», «дудос» → «DDOS»,
     «Разборки с …» → «исправление обработки …», «факапы» — убрать.
   - Форма — отглагольное существительное или инфинитив: «Обновление …», «Настройка …», «Починить …», «Перенос …».

5. **Разворачивать сокращения:** k8s → kubernetes, pdns → PowerDNS, CF → CloudFlare,
   X-F-F → X-Forwarded-For, серт → сертификат, траф → трафик/нагрузка, Мр → ревью/релиз (по смыслу).

6. **Убирать внутренние идентификаторы**, заменяя обобщением:
   - хосты и сервера (`app-legacy-01`, `blackbox`, `node-a/node-b`, `db07.dc-a.internal`) →
     «старый технический сервер», «production», «сервера clickhouse»;
   - номера окружений (`env-104857`) → «тестовые окружения»;
   - конкретные домены и внутренние адреса (`some-project.example`, `registry.internal`) →
     «домены», «docker registry»;
   - коды ошибок (`ERR_…`, 502/503) → «ошибки», «обрывы соединения».
   - Коды дата-центров (вида `dc-a`, `ams-1`) оставлять можно: они ничего не раскрывают.
   - **Публичные внешние сервисы и продукты оставляем как есть:** `CloudFlare`, `AWS`,
     `Jenkins`, `Artifactory`, `Vault`, `kubernetes`, `PostgreSQL`. Обобщать надо
     внутренние идентификаторы — свои хосты, номера окружений, ID клиентов, домены проектов, —
     а не общеизвестные названия: они делают формулировку конкретнее и одинаково пишутся
     на всех трёх языках.

   Смысл правила не в стилистике: акт уходит наружу и живёт у контрагента и в банке.
   Внутренние имена систем заказчика в нём делать нечего.

7. **Англоязычные/лог-заголовки переводить на русский по сути:**
   - «Failed Certs_Upgrade [домен]» → «Не продлеваются сертификаты для доменов из-за ошибок DNS-сервера»
   - «replication_status [хосты]» → «Удаление очередей репликации»

8. **Добавлять контекст, если заголовок слишком куцый** — где и зачем:
   - «Настроить auditd» → «Настроить auditd на серверах с хранением логов в openobserve»
   - «Заказать балансеров» → «Новые nginx-балансировщики»

9. **Номер задачи сохраняется без изменений.** Формат строки: `KEY - Название`.

10. **Эпик может попадать в несколько месяцев с разными формулировками** — по этапу работ месяца:
    `OPS-1300` → апрель «Подготовка нового хранилища sensitive данных»,
    май «Новые политики и схема хранения секретов».

11. **Только инженерная работа (devops/сисадмин), никакого консалтинга и менеджмента.**
    Вид деятельности исполнителя не предусматривает консалтинг, управление проектами и управление
    командами — формулировка обязана называть техническую работу руками и её артефакт (скрипт,
    конфигурация, сервис, мониторинг, инструкция), а не процесс, организацию или координацию:
    - «Автоматизация процесса on-call» → «Разработка скрипта автоматизации DevOps-дежурств»
    - слова-маркеры, которых избегать: «процесс», «организация», «координация», «управление»,
      «консультация», «аудит», «менеджмент», «сопровождение проекта».
    - Если непонятно, что за артефакт — смотреть комментарии задачи: там часто ссылка на
      репозиторий/MR с результатом.

12. **Коротко: одно действие + один объект.** Ориентир — 4–8 слов, 30–60 знаков, предел около 70.
    В название не выносим, *как именно* сделано: инструменты, протоколы, методы и обстоятельства
    остаются за кадром. Длинная формулировка выглядит как отчёт, а не как строка акта:
    - «Диагностика резолвинга доменов через распределённые DNS-пробы при просадке трафика» →
      «Диагностика причин просадки трафика у клиента»
    - «Техническое описание инструментов управления доменами и проверки их доступности» →
      «Документирование работы с доменами со стороны инфраструктуры»
    - «Включение API-интеграции с платёжным сервисом через переменные окружения приложения» →
      «Активация API-интеграции с платёжной системой»

13. **Формулировка должна ровно переводиться на языки акта** (`client.act_languages`
    в `profile.json`; какие именно — свойство клиента, а не этого навыка). Список из чата —
    источник для акта, где та же строка идёт на каждом из них, поэтому: конкретное действие +
    объект, без идиом и оборотов, теряющих смысл при переводе; технические термины (HTTPS,
    Vault, kubernetes, DDOS) — в написании, одинаковом на всех языках.

    Проверка простая: если строку приходится переформулировать при переводе, значит,
    в оригинале она описывает не работу, а рассуждение о ней.
