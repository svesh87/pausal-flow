# pausal-flow: движок документооборота ИП (Сербия, паушал)

Ядро — ежемесячный цикл с клиентом: список задач → акт и инвойс → уведомление банку →
бухгалтерский сервис и КПО. Вокруг него — счета поставщиков, налоги, банковские выписки
и сводный отчёт.

**Этот репозиторий — движок, он публичный.** Реквизитов, документов и имён здесь нет
и быть не может. Всё личное живёт в отдельном приватном репозитории данных: `profile.json`,
`months/`, `finance/`, `contracts/`, `signatures/`, `docs/history.md`. Образец конфига —
`profile.example.json`.

## Два корня

- **корень кода** — этот репозиторий: `scripts/`, шаблоны, навыки, документация;
- **корень данных** — приватный репозиторий: `profile.json` и всё, что перечислено выше.

Корень данных находится сам: переменная `TASKS_DATA` → каталог из `TASKS_PROFILE` → ближайший
вверх от текущего каталога каталог с `profile.json` → путь из локального файла `.tasks_data`
в корне движка (он вне git; нужен, чтобы гейты и пре-коммит, запускаемые **из каталога
движка**, видели настоящие реквизиты и проверяли, не утекли ли они) → корень кода
(одно-деревной режим: клон без данных, тесты, синтетические примеры). Подробности —
докблок `scripts/reqs.py`.

Внутри данных движок подключён симлинком и всегда зовётся `engine/…`. Пути в текстах —
относительные; абсолютных путей нет нигде.

## Ключевое соглашение

`ГГГГ_ММ` — **период работ, а не дата документа.** Задачи за июнь лежат в `months/2026_06/`,
отправляются в конце июня, а акт, инвойс и бланк банка по ним приходят в июле — и тоже лежат
в `months/2026_06/`. Нумерация актов сквозная с первого месяца работы.

## Структура движка

- `.claude/skills/` — навыки под каждый шаг: `setup`, `monthly-tasks`, `sign-docs`, `finance`,
  `signatures`;
- `scripts/` — подписание, проверка, парсер выписок, реестры, отчёт, КПО, импорт
  в бухгалтерский сервис, доктор, инициализация данных, синтетические примеры;
  `scripts/templates/pausal/` — шаблоны импорта; `scripts/tests/` — тесты и реестр кейсов;
- `docs/` — `setup.md` (настройка с нуля), `integrations.md` (роли и как их закрыть),
  `signatures.md` (библиотека образцов подписи);
- `tmp/` — вне git: планы (`FIX_PLAN_<дата>.md`), архив `old/`, прогоны и примеры.

## Структура данных

- `months/ГГГГ_ММ/` — всё по месяцу: `tasks.md` (задачи, формулировки на языках акта, реестр
  месяца), `acceptance_N[_signed].pdf`, `invoiceN.pdf`, бланк уведомления банка,
  `pausal/` (файлы импорта);
- `contracts/<контрагент>/ГГГГ_ММ_ДД/` — редакции договора; `versions.md` рядом говорит,
  какая действует. Суффиксы: `_signed` — подписан одной стороной, `_both_signed` — обеими;
- `finance/` — деньги и отчётность: `bank/raw/<валюта>/<год>/` (исходные выписки) и
  `bank/transactions_*.csv`, `payments/` (счета поставщиков и реестр), `taxes/` (документы
  налоговой и реестр платежей), `kpo/` (книги оборота по годам), `report.md` — сводный отчёт,
  `known_issues.md` — журнал разобранных тревог;
- `signatures/` — образцы подписи, **зашифрованы** в `samples.tar.gz.gpg`;
- `docs/history.md` — личная история форм документов, если владелец её ведёт;
- `.check_clean.local` — стоп-лист имён для проверки чистоты движка, вне git.

## Карта месяца

| Команда | Навык | Что происходит |
|---|---|---|
| «Собери задачи» | `monthly-tasks` | трекер → формулировки для акта → `months/ГГГГ_ММ/tasks.md` на ревью |
| «Отправь список в чат» | `monthly-tasks` | черновик в канал клиента: по секции на каждый язык из `client.chat_languages` |
| — | — | в треде появляются `acceptance_N.pdf` и `invoiceN.pdf` за месяц |
| «Подпиши документы из чата» | `sign-docs` | забрать из канала, подписать акт, проверить |
| «Отправь документы в чат» | `sign-docs` | черновик в тот же тред с подписанным актом |
| — | — | приходит платёж, банк присылает бланк письмом |
| «Подпиши документы банка» | `sign-docs` | забрать из почты, заполнить, подписать, проверить |
| «Отправь документы в банк» | `sign-docs` | окно ответа на письмо банка с четырьмя вложениями |
| «Выгрузи в pausal.rs» | `sign-docs` | два файла импорта в бухгалтерский сервис (артикул + счёт) |
| «Обнови книги КПО» | `sign-docs` | пересобрать `finance/kpo/` |
| — | — | банк подтверждает зачисление письмом |

Шаги выполняются раздельно, по команде, с проверкой владельцем между ними. Реестр месяца
наполняется по ходу: даты инвойса — на шаге документов месяца, дата и сумма оплаты —
на шаге банковских документов.

## Финансы помимо цикла — навык `finance`

| Команда | Что происходит |
|---|---|
| «Обнови финансы» | всё оптом: банк → счета поставщиков → налоги → пересборка → одна сводка |
| «Обнови банк» | новые izvod из почты и выгрузки eBank → `parse_izvod.py --ingest` → CSV, сверка цепочки остатков |
| «Собери счета» | новые счета поставщиков из почты → `finance/payments/ГГГГ/` + реестр |
| «Обнови налоги» | новые документы налоговой → `finance/taxes/statements/` → реестр |
| «Обнови отчёт» | `build_report.py` → `finance/report.md` |
| «Прими документы» | разобрать `tmp/inbox/`: определить тип каждого файла и разложить |
| «Прими договор» | разобрать договор из `tmp/inbox/` → `contracts/` (навык `sign-docs`) |

## Настройка и подписи — навыки `setup` и `signatures`

| Команда | Что происходит |
|---|---|
| «Настрой окружение» | инструменты, скелет приватного репозитория, `profile.json` по блокам, интеграции, проверка |
| «Проверь окружение» | `scripts/doctor.py` и разбор того, что он показал |
| «Собери библиотеку подписей» | сканы → набор PNG → разметка → зашифрованный контейнер |

Всё производное пересобирает `scripts/rebuild_all.sh`. Шаги идемпотентны: приёмка пропускает
уже лежащие файлы, парсер дедуплицирует операции, каждый динарский izvod сверяется с итогами
дня, цепочка остатков — между izvod-ами.

## Правила работы

- **Планы, черновики и временные исследования — только в `tmp/`.** Именование
  `tmp/FIX_PLAN_<ГГГГ-ММ-ДД_ЧЧ-ММ-СС>.md`, прежние планы уезжают в `tmp/old/`, актуальный
  остаётся до появления следующего.
- **На нетривиальную работу — план-черновик** со статусом «черновик, ждёт одобрения
  владельца»; выполнение только по явной команде. Настоящие развилки (архитектура, объём
  работ, внешние настройки) задаются в чате **до** финализации плана и вписываются в него
  как принятые решения; раздела «Вопросы владельцу» в плане нет. Мелкие дефолт-решения
  помечаются «поправь при ревью, если не согласен».
- **Порядок выполнения:** код → документация и комментарии в коде → гейты → статусные правки
  (фактические цифры только после гейтов) → сквозная проверка связности последним шагом.
- **Комментарии в коде — такой же объект работы, как документы.** В плане им отводится
  отдельный шаг с адресным перечнем (файл + якорь), а не строка «поправить комментарии»:
  докблоки и комментарии у констант устаревают первыми и молча, потому что их не видно
  ни в тестах, ни в гейтах.
- **Коммитящаяся часть не ссылается на файлы в `tmp/`** — ни путей к планам, ни упоминаний.
  Само соглашение «черновики и прогоны — в `tmp/`» описывать можно: это правило работы,
  а не зависимость от содержимого папки.
- **Правки движка и правки данных — разные коммиты в разные репозитории.**
- **Системный `/tmp` прибирать за собой** в конце сессии; чужое там не трогать.
- **Не коммитить и не пушить без команды владельца.**

### Окружение

`python3 -m venv .venv` и `.venv/bin/pip install -r requirements-dev.txt`. Если `venv` падает
на отсутствии `ensurepip`, использовать `virtualenv .venv` — системных пакетов не требует.
**Ставить системные пакеты самому нельзя**: если без установки не обойтись — остановиться
и попросить владельца.

### Гейты перед сдачей работы

```bash
.venv/bin/ruff check scripts/            # линтер обязан быть зелёным
.venv/bin/pytest -q                      # тесты зелёные, реестр кейсов полон
scripts/check_clean.sh                   # в движке нет ничего личного
scripts/rebuild_all.sh                   # прогон всех сборок (если данные подключены)
git diff --stat                          # по сгенерированному — пусто, кроме намеренного
git diff --check -- ':(exclude)finance/bank/*.csv'
```

Из проверки пробелов исключены CSV операций: в назначениях платежей банк присылает текст
с хвостовыми пробелами и возвратами каретки, они попадают в поле как есть и это не дефект.

Покрытие мерится **бизнес-кейсами, а не строками**: `scripts/tests/CASES.md` — таблица
«кейс → тест», каждая строка обязана иметь живой тест, новая функциональность добавляет
строку вместе с тестом. Это проверяет сам тестовый набор.

## Границы (действуют всегда)

- **Подписанное и отправленное не переподписывается и не перегенерируется** без явного
  разрешения владельца: меняются `/ModDate` и подписи внутри PDF, и документ перестаёт
  совпадать с тем, что лежит у контрагента. Касается актов, бланков банка, договоров, книг
  КПО за закрытые годы, выгрузок в бухгалтерский сервис. Скрипты подписи отказываются писать
  поверх существующего файла без `--force`.
- **Отчётность прошлых лет не переписывается** — книги `finance/kpo/kpo_ГГГГ.pdf` за закрытые
  годы и всё, что уже сдано. Пересборка задним числом — только с прямого разрешения
  (`--allow-past`); расхождение данных с закрытым документом — повод остановиться
  и разобраться, а не перегенерировать.
- **Документы за пределами репозитория** — только по просьбе владельца и только на чтение;
  папку он называет в запросе. Своих внешних путей репозиторий не знает.
- Готовые документы в корнях папок месяцев — уже отправленные, они эталон для сверки.
  Прогоны и эксперименты — в `tmp/test/<месяц>/`.
- **Ничего не уходит наружу автоматически.** В мессенджер — только черновик (у Slack MCP это
  `slack_send_message_draft`, не `slack_send_message`: прямая отправка добавляет «Sent using
  Claude»). В почте — только окно ответа (`replyToMessage` без `skipReview`), `sendMail`
  не использовать. Жмёт «Отправить» владелец.
- Подписанный документ **всегда проверяется** до отправки (`scripts/verify_signed.sh` плюс
  взгляд на область подписи).
- **Генерируемые файлы руками не правятся** — перезапись затрёт правки. Что чем собирается —
  таблица в `README.md`.
- Формы документов меняются. Скрипты падают с понятным сообщением вместо порчи документа;
  **если разобрать изменение самостоятельно не получается — остановиться и спросить**,
  показав, что именно не совпало. Не подписывать наугад.
- Формулировки задач — только инженерная работа devops/сисадмина с артефактом. Вид
  деятельности исполнителя не предусматривает консалтинг, управление проектами и управление
  командами.
- Личные счета в репозиторий не складываются и в отчёт не подмешиваются.
