# Библиотека образцов подписи

Электронная подпись здесь — это картинка настоящей подписи, вставленная в PDF инкрементальным
обновлением. Никакой криптографии в документе не появляется: и банк, и клиент принимали
подписанный таким образом документ, квалифицированной подписи никто не спрашивал. Если
у кого-то спросят — этот способ не подойдёт, и это будет видно по отказу, а не заранее.

Раз документ уходит картинкой, качество набора образцов определяет, выглядит он подписанным
или распечатанным штампом.

Порядок работы с агентом — навык `signatures` («Собери библиотеку подписей»). Здесь то, что
нужно понять человеку.

## Почему набор, а не один файл

Подпись руки каждый раз немного разная: наклон, длина хвоста, плотность нажима. Один и тот же
файл, вставленный пиксель в пиксель в двенадцать актов, различим глазом сразу — и по нему
видно, что подпись электронная. Набор из 10–15 образцов даёт в каждый документ свой вариант;
скрипты выбирают образец случайно, а для двух колонок акта берут два разных.

Второе следствие: набор нельзя переделывать «поаккуратнее» после того, как документы ушли.
В отправленных актах стоят прежние образцы, и это нормально.

## Что сканировать

1. **Лист с образцами** — 10–15 подписей от руки на белой бумаге, синей шариковой или гелевой
   ручкой, с интервалами, чтобы не сливались. Сканировать не ниже 600 dpi.
2. **Уже подписанные документы** — банковские формы, договоры, карточка счёта. Там подпись
   стоит в рабочих условиях и выглядит естественнее, чем на чистом листе; такие образцы обычно
   и получаются лучшими.
3. Фотографии с телефона годятся хуже (тени, перспектива, неровный фон), но если это всё,
   что есть, — работать можно.

Синие чернила — не прихоть: по синему каналу подпись отделяется от чёрного текста документа
и от серого фона бумаги одним порогом. Чёрную ручку тоже можно вытащить, но придётся
разделять подпись и типографику руками.

## Что происходит со сканом

Конвейер (агент выполняет его по навыку `signatures`, разово; отдельного скрипта нет —
параметры каждый раз подбираются под скан):

1. рендер в 900 dpi — тройное суперсэмплирование относительно 300: последующее уменьшение
   съедает шум сканера, а не край штриха;
2. выделение синих чернил по разнице каналов; чёрный текст, линии, галочки и печати отсеиваются;
3. чистка: мелкие компоненты (пыль, точки печати), кадры с чужой подписью или элементами
   документа, перечёркнутые образцы;
4. кроп по рамке чернил плюс поле ~240 px: скрипты позиционируют образец по базовой линии
   письма, и им нужно место;
5. плотность штриха: гладкое плотное ядро (размытие плюс `smoothstep`), обратно наложенная
   фактура чернил из оригинала, бледные окончания подняты гаммой, а не обрезаны порогом;
6. цвет чернил остаётся оригинальным попиксельно, шум цвета убирается усреднением
   по чернильным пикселям окна 5×5 без подмешивания фона;
7. сохранение в RGBA PNG с прозрачным фоном — **без фильтров строк**: скрипты разбирают PNG
   сами, без внешних библиотек.

Библиотеки для шагов 2–6 (Pillow, numpy) в зависимостях движка не числятся: они нужны один
раз, при сборке набора, и ставятся в отдельное окружение.

## Разметка

```bash
python3 scripts/sig_metrics.py <папка с PNG>
```

Считает по каждому образцу: рамку чернил, **базовую линию письма** (строку, где стоит основная
масса штрихов, без учёта хвостов), нижний вынос, пропорцию и масштаб. Результат — `metrics.json`
для скриптов и `METRICS.md` для глаз.

Зачем базовая линия: у части образцов длинный нижний вынос, и если ставить их по крайнему
нижнему пикселю, такие подписи встают заметно выше остальных. По базовой линии положение
относительно линии документа одинаково у всех, а хвосты естественно её пересекают.

Зачем нормировка по площади чернил, а не по ширине: пропорции образцов расходятся на ±25%,
и «плоские» подписи при нормировке по ширине выглядели бы мельче остальных.

Разметка пересчитывается после **любого** изменения набора.

## Хранение

```bash
python3 scripts/signatures.py --pack <папка с PNG>    # signatures/samples.tar.gz.gpg
python3 scripts/signatures.py --list                  # что внутри контейнера
```

В git идёт только контейнер, зашифрованный на GPG-ключ из `profile.json` (`gpg.recipient`),
плюс разметка. Открытые PNG не коммитятся никогда: `signatures/*.png` закрыт `.gitignore`,
а пре-коммит репозитория данных проверяет индекс. Скрипты подписи расшифровывают контейнер
**в память** при каждом запуске — открытых файлов на диске не появляется вообще.

Один архив, а не файл на образец, — потому что шифровальный подключ обычно живёт на токене
и каждый вызов `gpg` требует касания или PIN. Один контейнер = один вызов за запуск, даже
когда акту нужны два разных образца.

## Проверка

```bash
python3 scripts/make_examples.py tmp/example-data
python3 scripts/sign_pdf.py tmp/example-data/months/2026_06/acceptance_1.pdf \
                            tmp/example-data/acceptance_1_signed.pdf
scripts/verify_signed.sh tmp/example-data/months/2026_06/acceptance_1.pdf \
                         tmp/example-data/acceptance_1_signed.pdf --look
```

Смотреть глазами: подпись по центру поля, базовая линия чуть ниже линии документа, хвосты
пересекают линию, размер одинаковый в разных документах. Если размер не тот — дело
в разметке, а не в образце.

## Чего не делать

- не хранить сканы документов, из которых вырезаны образцы, в репозитории: там и подпись,
  и данные документа;
- не держать второй набор «до обработки»: собрать заново из сканов дешевле, чем хранить;
- не подписывать документ, который уже отправлен, заново — даже если новый набор лучше;
- не выкладывать открытые PNG никуда, включая приватный репозиторий. Подпись и так стоит
  в каждом отправленном документе, так что «единственным источником утечки» набор не является;
  но готовый к вставке образец на прозрачном фоне переиспользовать заметно проще, чем
  вырезку из скана, — а хранить его зашифрованным ничего не стоит.
